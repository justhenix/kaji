# Live head tracking: fixes and executed evidence

Windows desktop verification, 2026-11-01, Asia/Jakarta. No product GUI, Pi runtime or agent orchestration was added. Camera observations remain local; diagnostic JSON contains geometry/status, not camera images.

The original two-second startup failure is addressed. Real webcam sessions now reach calibration and tracking, execute native cursor movement and dwell, and stop safely. **Full human acceptance on Calculator's 7 is still FAIL / incomplete:** the completed two-minute trial produced two non-target dwells, not a verified 7-button effect. A passing native replay must not be presented as human acceptance.

## Causes and corrections

1. **Cold inference was submitted as an actionable first frame.** Creating the MediaPipe detector did not warm `detectForVideo`. Rust was armed before that first inference, so cold work could arrive beyond the unchanged 180 ms age limit. The capture loop now warms on a real decoded camera image before native authorization, discards that observation, then timestamps every subsequent image at capture. A controlled 650 ms first inference reproduces the old failure mechanism and verifies the corrected order. Actual later native warm-ups took about 82–84 ms. The original saved failure had zero processed frames and only a generic rejection; its exact rejection branch cannot be recovered retrospectively.
2. **The worker's clock was a hypothesis, not the cause found.** The worker already echoed the capture timestamp from the webview; it did not replace it with its own `performance.now()`. Native time is translated once using the initialization response. Sequence and capture times remain monotonic. IPC/inference delay remains part of frame age; no late sample is restamped to appear fresh. Rejection messages now identify the actual reason and include capture/native time, age, sequence and session start.
3. **Detection thresholds were too aggressive for the supplied seating view.** The bundled CPU detector was run against the user's later supplied screenshot: thresholds 0.7 found zero faces in 30 observations, while the SDK default 0.5 found a usable face in all 30. Its normalized eye span was 0.06449. These are repeated screenshot observations, not 30 live-camera frames or an accuracy benchmark. Production now uses the documented defaults. The actual live transport was tested separately.
4. **Raw face count and a rigid foreground lock rejected a person with a background portrait or changing distance.** Rust now associates the clearly dominant foreground candidate, adapts its confirmed eye span, allows bounded movement across detection gaps, and excludes previously observed background candidates. Comparable/ambiguous candidates pause input. It does not claim to determine whether a face is alive, nor provide biometric identity verification. It never automatically promotes the learned portrait when the operator disappears.
5. **Calibration discarded useful evidence after isolated landmark noise.** A 120 ms pose filter feeds a rolling median window. Calibration still requires at least 20 inliers, at least 80% inliers within the original 0.025 pose tolerance, a current inlier, and at least one second of stable evidence. A recorded failed live trace that had never calibrated reaches neutral after 23 observations through the corrected core. The subsequent final replay caught a separate buffer defect: capping at 30 observations made a full second impossible at 30 FPS. The window now retains 1.5 seconds, bounded to 256 observations, sufficient for the native executor's maximum observation rate. A regression first failed at 30 FPS and now passes at 15, 30 and 60 FPS without reducing the duration requirement.
6. **Recoverable loss and motion cadence made tracking appear to freeze.** No-face/ambiguity pauses input immediately instead of terminating a healthy stream. Reacquiring the same operator within one second retains neutral; longer loss requires calibration again. Native 8 ms ticks integrate the latest fresh filtered pose instead of moving only on approximately 16 camera observations per second. Raw neutral posture stops without coasting. No pose is integrated beyond its original 180 ms lifetime.
7. **Dwell and verification ended healthy attempts prematurely.** Moving ticks now record deliberate departure without being allowed to click. Missing-operator time is excluded from dwell and cannot rearm a completed click. Target-scoped dwell outside Calculator is suppressed while tracking continues. The human verifier records the native successful click coordinate, continues after non-target dwells, checks 7's actual rectangle and Calculator's resulting value, and explicitly records a stopped status even on timeout. Late sensor shutdown preserves the first native stop reason, and cancellation during initialization cannot rearm execution.

## Reproduce

Use [Windows verification instructions](WINDOWS-VERIFICATION.md) for the complete build, deterministic tests, opt-in native safety, UIA, replay and human check. For the live check, keep Calculator visible and use `verify-head.ts --hwnd <current HWND> --seconds 120`. `head-live.json` distinguishes initializing, no-face, calibration progress and tracking. Keyboard/mouse activity intentionally stops the session; Escape remains the emergency stop.

Freshness rejection (180 ms ingress / 200 ms pending execution), source watchdog (250 ms), observer heartbeat (300 ms), session authorization, exclusive input ownership, physical target checks and emergency/manual stop remain enforced by Rust. No validation timeout was widened to obtain these results.

Primary references: [Google Face Landmarker web options](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js) documents the 0.5 confidence defaults and the absence of built-in smoothing with multiple faces; [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/) defines time origins and monotonic timestamps.
